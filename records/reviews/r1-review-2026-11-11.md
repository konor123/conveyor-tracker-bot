## 발견

### P1 — 수락된 goal을 실행 중으로 예약하지 않아 정지 유지 중 받은 goal이 해제 뒤 실행됨

- 위치: `src/robot_control/robot_control/robot_controller_node.py:227`~240, `:376`~384.
- `_on_goal`은 `_active_goal`을 검사만 하고 ACCEPT한다. `_active_goal=True`는 나중 `_execute`에 들어와서 설정한다. 따라서 정지 유지 중 goal 수락 → 실행 callback 시작 전 작업자 해제 → 실행 순서에서 해제가 성공하고, 유지 중 받은 goal이 STOPPED로 끝나지 않고 이동한다. SPEC-010 4.5절의 “정지 유지 중 받은 skill goal은 지령 없이 CANCELED(STOPPED)”와 불일치한다.
- 대역은 `mock_robot_controller_node.py:91`~96에서 수락 시 `_busy=True`를 예약하므로 동일 구간의 해제는 GOAL_ACTIVE로 거부한다. 실제/대역 계약도 다르다. 수락 뒤 Stop이 들어오고 실행 전 해제되는 순서 역시 실제 노드에서는 outstanding goal을 보지 못한다.
- GCE에서 production `_on_goal`, `_on_params`, `_execute`를 AST로 그대로 추출해 실제 `StaticSkillExecutor`와 `SimulatedBackend(move_time_s=0)`로 재현했다. 출력: `accept=ACCEPT active=False`, `release=True`, `result=0 reason='' backend_calls=['move_line'] tcp=[0.1,0.0,0.1]`. 실제 ROS executor 스케줄 및 실기 움직임은 재현하지 않았지만 허용되는 호출 순서에서 production 판정과 fake 지령 호출을 확인했다.
- 권고: 수락 시점에 outstanding goal을 원자적으로 예약하고 종료 때 해제한다. Stop 당시/수락 당시 latch 상태를 goal 단위로 보존하거나, outstanding goal이 있으면 작업자 해제를 거부하여 이전 goal이 재개되지 않게 한다. 수락과 실행 사이 barrier를 둔 C/U 회귀를 추가한다. 단순히 `_execute` 시작에서만 latch를 읽는 시험으로는 부족하다.

### P2 — 유지 중이 아닌 해제가 backend 정지를 해제해 '무동작 성공' 계약 위반

- 위치: `src/robot_control/robot_control/robot_controller_node.py:377`~385, `src/robot_control/robot_control/stop_latch.py:48`~49.
- `StopLatch.release()`는 latch가 없을 때 빈 문자열을 반환한다. 노드는 이를 실제 해제 성공과 구분하지 않아 매번 `backend.reset_stop()`을 호출한다. 빈 사유도 latch가 없으면 backend 정지를 풀 수 있다.
- GCE production `_on_params` + 실제 SimulatedBackend 재현: `stop_latch.latched=False`, `backend.stop()` 뒤 `stop_release_reason=''` 설정 → `before no-op: True`, `after no-op: False`. 예를 들어 lifecycle deactivate도 backend.stop()을 호출하므로 이 상태는 StopLatch 없이 실제로 생긴다. 비활성에서 곧바로 지령이 실행된다고 주장하는 것은 아니다.
- SPEC-010 4.5절은 유지 중이 아닌 설정이 아무것도 하지 않는다고 명시한다. 현재 U 시험은 StopLatch 객체만 보므로 backend 부작용을 놓친다.
- 권고: 해제 결과에 실제 latched→clear 전이 여부를 구분하고 그 전이에만 backend reset을 수행한다. no-op 요청의 backend 호출 0회, 실행 중 no-op, lifecycle 정지 상태를 시험한다. latch 해제와 backend reset 사이에 새 Stop이 들어오는 경쟁도 함께 동기화해야 한다.

### P2 — I0가 WAIT_CAP에서 Stop을 주입했음을 보장하지 못하고 감시 지연을 상태 실패로 혼동

- 위치: `src/drop_bringup/test/test_i0_integration.py:554`~571.
- `any(state == WAIT_CAP)`는 과거 상태 수신을 확인할 뿐 Stop 수신 당시의 상태가 아니다. 이어 `GetParameters(skill_run_count)` 왕복까지 수행하므로 그 사이 PLAN_INTERCEPT/APPROACH 등으로 넘어갈 수 있다. `n_stop`은 Stop 응답 후에 잡아 그 전 상태 전이도 검사에서 제외한다.
- robot latch는 즉시 지령을 차단하지만 orchestrator는 다음 controller heartbeat를 받아야 Stop을 알 수 있다. 정상 조건에서도 nominal 0.1 s 발행 주기와 수신 지연이 있고 watch timer는 0.05 s다. `pending_fault()`가 동기 `_watch()`를 호출해 추가 timer 지연을 줄이지만 수신 전 캐시의 0은 바뀌지 않는다. 이 동안 비로봇 단계 진행/차단될 skill 전송은 가능하다. “로봇 지령 0회”와 “Stop 직후 모든 상태가 WAIT_CAP/PROTECTIVE_STOP/WAIT_OPERATOR”는 같은 보장이 아니다.
- 따라서 현재 시험은 정상 latch 구현을 시간 위상에 따라 실패시킬 수 있고, 이미 다음 skill이 시작된 뒤 Stop해도 이전 skill_run_count를 잡는 시점에 따라 잘못된 구간을 검증할 수 있다. 순수 TC-ORC-012는 fault를 즉시 주입하므로 이 DDS 경계를 검사하지 않는다.
- 권고: WAIT_CAP 선택/관측 응답을 시험용 barrier 또는 시나리오로 유지하고, controller가 idle인 상태에서 Stop 수신을 확인한 뒤 barrier를 해제한다. 주입 전후 sequence·steady 시각을 보존하고, controller 지령 0회와 heartbeat 수신 뒤 L4 전이를 각각 판정한다. 임의 sleep만 늘리지 않는다. 해제 후 재개도 새로운 0 heartbeat·ready=true가 orchestrator에 반영된 것을 확인하면 stale 101에 의한 실패를 분리할 수 있다(현재 `_reset_cycle_clock`이 즉시 상태 발행 + 0.08 s sleep을 제공하나 수신 확인 자체는 아니다).

## heartbeat 공백 원인 판단

**별도 callback group·4 threads는 가능한 완화지만 원인 규명이나 해결 증거는 아니다. 수신 측이 더 그럴듯하다고 단정할 코드 근거도 없다.**

1. 대역 skill/Stop은 이미 ReentrantCallbackGroup이었다. 기존 3 threads에서도 보통 skill 실행 1개 + Stop 대기 1개 + 타이머 1개는 가능하다. `_run`은 추가로 heartbeat/status를 직접 발행한다. 그러므로 “skill 하나가 default group을 막아 heartbeat가 끊김”만으로 idle 구간 관측을 설명하기 어렵다.
2. 기존 heartbeat/status는 default group의 parameter 서비스와 직렬화된다. t0 설정은 부모 `_on_params`에서 즉시 상태/heartbeat 발행도 한다. 느린 parameter 처리·publish·스케줄링이 있으면 타이머 분리는 도움이 된다. 다만 코드에 정상 parameter 요청이 300 ms 이상 대기하는 명백한 sleep은 보이지 않는다. executor thread 증가는 예약된 heartbeat 전용 스레드나 실행 우선권을 보장하지 않는다.
3. supervisor는 단일 스레드 `rclpy.spin`, 모든 callback이 default group이다. `_tick`은 비동기 Stop을 쓰고 미완료 future를 기다리며 block하지 않는다. 수신 callback도 짧다. 노드 전체 CPU scheduling 지연이나 DDS backlog 뒤 timer가 먼저 실행되면, 실제 발행은 계속되었어도 callback에서 찍는 heartbeat 나이가 300 ms를 넘을 수 있다. 단일 스레드 자체만으로 원인을 확정할 수 없다.
4. `SupervisorMonitor`는 첫 controller heartbeat 이전에는 손실을 판단하지 않는다. 따라서 “controller가 아직 시작하지 않음”만으로 이 Stop은 나오지 않는다. 첫 heartbeat 뒤 startup 부하/발견·수신 공백은 가능하다. I0 `_wait_ready`는 각 역할의 ACTIVE heartbeat를 1회 이상 본 것과 TaskStatus 존재만 확인하며, 지속 heartbeat 안정성/RobotStatus.ready/controller latch clear는 확인하지 않는다. 이 때문에 기동 과도기의 Stop이 그대로 다음 PRECHECK를 막는 가설은 타당하다.
5. 정상 복구 뒤 supervisor monitor의 reason은 사라져도 controller latch는 의도대로 남는다. t0 reset도 `_stop_latched`를 풀지 않는다. Stop 유지 설계를 제거하거나 timeout을 임의 확대해서 시험을 통과시키는 것은 원인 해결이 아니다.
6. 별도 group에서도 `_on_status`와 heartbeat가 같은 그룹이며, heartbeat는 skill 루프/parameter callback에서도 직접 호출한다. 이들은 group 상호배제 밖에서 호출된다. 따라서 발행 진단에는 source seq와 publish 직전 steady, 수신 DDS timestamp, callback 진입 steady, supervisor tick의 마지막 controller 수신 시각을 함께 기록해야 한다. 단순 관찰자 한 곳의 간격만으로 발행 공백과 수신 지연을 나눌 수 없다.

권고 PC 검증: 같은 변경본으로 기동부터 I0 종료까지 위 시각을 수집해 idle/skill/Stop/parameter 구간별 최대 gap을 비교하고 반복 실행한다. supervisor가 Stop을 낸 시각이 첫 heartbeat 직후인지, publisher gap도 동반되는지부터 구분한다. 이번 worker는 PC 접속 금지에 따라 수행하지 않았다.
