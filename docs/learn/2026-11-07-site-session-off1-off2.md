# OFF-1·OFF-2: 측정값에서 무엇을 배웠나

이 문서는 11월 7일 현장 자료를 읽는 안내다. 원시 결과는 [OFF-1](../../records/sessions/OFF-1-2026-11-07.md), [OFF-2](../../records/sessions/OFF-2-2026-11-07.md)에 있다. 자료 확보·예비 동작 확인과 G0·G1 합격을 구분해서 읽는다.

## D455: 센서가 내보낸 프레임과 프로그램이 받은 프레임

D455 연결 후 공장 내부 파라미터와 ChArUco 보드를 확인했다. 초기 ROS 수신은 불안정했지만 FastDDS SHM 64 MB 프로파일 적용 뒤 image_raw 29.97 Hz, stamp 간격 중앙값 33.37 ms, 수신−stamp 지연 p50 22.2 ms·p95 25.3 ms를 관측했다([OFF-1](../../records/sessions/OFF-1-2026-11-07.md), [프로파일](../../src/drop_bringup/config/fastdds_large_shm.xml)). 센서의 촬영률이 정상이어도 전송·구독 경로에서 전달이 막힐 수 있다는 사례다.

별도 SDK 관측은 RGB 1280×800/30, depth 1280×720/30으로 약 180초간 각 5359 frameset을 수집했다. RGB 지연 p95는 16.458 ms, depth는 16.498 ms였지만 depth 최대는 316.171 ms였다. 양쪽 stamp 역행은 없었고 프레임 번호 건너뜀은 RGB 36·depth 37이었다. SDK 동기화·소비 과정과 센서 자체 누락을 분리하지 못했으므로 이 값을 센서 드롭 수로 확정하지 않는다([시각 관측](../../records/sessions/d455-timing-2026-11-07.md)).

배운 점: 촬영 stamp, 수신 시각, 소비 시각을 따로 기록해야 지연의 위치를 좁힐 수 있다. SDK global_time 관측과 ROS 전송 지연은 측정 경로가 달라 직접 같은 수치로 비교하지 않는다.

흔한 함정: 평균 30 Hz만 보고 최대 공백을 놓치거나, 짧은 회귀 기울기를 장시간 센서 drift로 확정하는 것이다. RGB 노출·WB 고정과 전체 시각 게이트도 완료되지 않았다.

직접 해 보기(읽기 전용):

```bash
cat records/sessions/d455-timing-2026-11-07.md
cat src/drop_bringup/config/fastdds_large_shm.xml
```

## Hand-eye: 영상에 잘 맞는 변환과 물리 검증

고정 카메라의 좌표를 로봇 베이스 좌표로 옮기려면 외부 변환이 필요하다. 로봇 자세와 표식 영상의 대응을 모아 카메라 위치와 TCP에서 표식까지의 오프셋을 함께 추정했다. 최종 배치의 50자세 자료와 원시 영상·계산 입력은 [보정 아카이브](../../records/calib/2026-11-07-final-layout/ARCHIVE.md)에 있다.

[계산 보고서](../../records/calib/2026-11-07-final-layout/result/report.md)의 후보 해는 HOLDOUT 재투영 오차 1.147 px를 기록했다. 하지만 독립 TCP 접촉 검증점은 0개이며 G1_pass=false다. 재투영은 모델이 영상을 얼마나 잘 설명하는지 보여 주지만, 표식 크기·내부 파라미터·좌표 오프셋의 체계 오차까지 제거했다는 뜻은 아니다. 작업 평면에서 독립 접촉점 최소 20개로 XY p95≤1.0 mm·최대≤2.0 mm를 확인하는 조건은 남아 있다. 이 수치는 현재 명세의 합격 기준이며 실측 통과값이 아니다.

배운 점: 학습에 사용하지 않은 영상 자세의 검증과 별도 물리 기준을 이용한 검증은 서로 다른 질문에 답한다.

흔한 함정: px 단위 오차를 바로 mm 정확도로 읽거나 candidate YAML을 운영 보정값으로 배포하는 것이다. 현재 후보는 물리 검증 전이다.

직접 해 보기:

```bash
cat records/calib/2026-11-07-final-layout/result/camera_extrinsics_candidate.yaml
rg -n 'HOLDOUT|independent_touch|G1_pass|배포' records/calib/2026-11-07-final-layout/result/report.md
```

## 네 가지 벨트 조건과 영상 품질

아날로그 조절부에는 수치 다이얼 값이 없어 조건을 stable-current, fast-1, fast-2, maximum으로 구분했다. 현재 조명 하나에서 네 조건을 확보했으며 mm/s·독립 속도 GT·두 번째 조명은 미측정이다. 단순 HSV의 픽셀 속도 증가는 영상상 조건 차이를 확인하는 보조 자료다([조건 목록](../../records/bench/moving-conditions-2026-11-07.csv), [OFF-1](../../records/sessions/OFF-1-2026-11-07.md)).

fast-1 장시간 bag의 첫 RGB 한 장은 약 50.51초 오래됐고 대응 CameraInfo가 없었다. 실제 publisher의 Transient Local QoS와 부합하는 retained 선두 샘플이었다. 전체 stamp 범위만 계산하면 관측 시간이 부풀려진다. 현재 RGB/CameraInfo 쌍을 골라 얻은 관측 창은 64.4821초였다. fast-2에서는 depth에 오래된 선두 샘플이 남아, RGB만 최신 수신을 확인하는 절차의 한계를 드러냈다.

maximum에서는 두 스트림의 최신 수신을 확인해 선두 문제를 줄였지만 녹화 중 지연·누락이 있었다. 따라서 오래된 선두 샘플, 실제 전달 지연, 프레임 공백을 각각 기록하고 원본을 보존했다. “65초 녹화 명령”도 실제 관측 65초를 보장하지 않는다.

공유용 자료는 원본 bag 8개 80.08 GB에서 RGB 8개·깊이 미리보기 6개, 합계 302.35 MB로 만들었다. 고정 30 fps MP4는 보기 위한 복사본이며 실제 시간 간격은 frames.csv의 원래 header stamp와 bag 수신 시각으로 분석한다. 깊이 미리보기는 손실 압축이라 정밀 깊이 복원에 사용하지 않는다([영상 설명·해시·프레임 수](../../records/media/2026-11-07/README.md), [bag 인덱스](../../records/bags.csv)).

배운 점: 원본 보존, 대응 프레임 검사, 품질 결함 표시는 데이터 세트의 일부다.

흔한 함정: 영상 재생 시간으로 지연을 재거나 조건명 maximum을 로봇의 허용 최고 속도로 읽는 것이다. 세 속도×두 조명 자료 요건과 현장 tracking 합격은 충족됐다고 할 수 없다.

직접 해 보기:

```bash
cat records/bench/moving-conditions-2026-11-07.csv
python3 -m json.tool records/media/2026-11-07/manifest.json | head -60
```

## E0509: 지령 주기·추종 지연·정지는 다른 측정

로봇 단독 시험에서는 servol·speedl을 50/100 Hz로 비교했다. speedl 100 Hz의 지연은 32 ms, 추종 오차 p95는 원시 0.97 mm·시차 보정 후 0.18 mm였다. stale 지령 시험은 20/20 정지·재개 0회, 정지까지 p95 149 ms, 마지막 지령 뒤 최대 이동 2.34 mm였다([OFF-2](../../records/sessions/OFF-2-2026-11-07.md)). 지령 간격은 송신의 규칙성, 지연은 반응의 시간차, 추종 오차는 위치 차이이므로 각각 필요하다.

이후 D455·녹화·ArUco 참조 처리 부하를 함께 걸었을 때 speedl 100 Hz는 간격 p99 10.146 ms, 지연 29 ms, 원시/시차 보정 p95 0.903/0.062 mm였다. 이것은 production vision_node 부하 검증이 아니다. servol 50 Hz는 실제 X 범위가 0.0036 mm여서 목표 왕복을 수행하지 못했다. 이어진 stale 시험도 실제 이동이 없어 무효 처리했다. “움직이지 않던 로봇이 계속 정지함”을 정지 성공으로 세지 않은 것이 핵심이다.

배운 점: 정지 시험에는 먼저 유효한 움직임이 있었는지를 확인하는 전제조건이 필요하다. 시차 보정 오차만 낮아도 해제 타이밍의 지연 문제는 남는다.

흔한 함정: 단독 조건의 정지 성공을 부하 조건·cancel·통신 단절·프로세스 종료 경로 모두의 성공으로 확대하는 것이다. 부하 중 스트림 무응답 원인도 미확정이다.

직접 해 보기(실기 지령 없이 자료만 읽는다):

```bash
rg -n '20/20|무효|무응답|지연|실제 X' records/sessions/OFF-2-2026-11-07.md
```

## 그리퍼 경로와 현장 안전

그리퍼는 E0509 플랜지 RS-485와 제어기 DRL을 경유한다. 일회성 DRL로 읽기·개폐를 확인했지만 상주 DRL 루프·개방 지연 분포·스트림과 동시 동작까지 입증하지는 못했다. 100 pulse 왕복은 위치값이 바뀌어도 현장 작업자가 움직임을 보지 못했고, 500 pulse 왕복에서 움직임을 확인했다([인계 기록](../../records/sessions/gripper-takeover-2026-11-07.md)). 레지스터 응답과 물리 동작 관찰을 함께 기록해야 하는 이유다.

제조사 하드웨어 Goal Position 범위 0~1150 pulse와 당시 현장 CLI 끝점 750 pulse는 의미가 다르다. 참고 구현의 0~750 반전 규약을 프로젝트 제어에 가져오면 안 된다. 전류 도구 기본값·상한은 사용자 지시로 100 mA로 낮췄지만, 해당 인계 기록의 실제 100 mA 쓰기는 기동 전 거부되어 장비 적용 확인이 보류됐다. 과거 200 mA 실행 기록도 당시 값으로 남긴다([현재 작업 규칙](../../AGENTS.md), [당시 인계](../../records/sessions/gripper-takeover-2026-11-07.md)).

배운 점: 한 지령 경로의 소유자를 정해야 중복 드라이버·중복 명령을 막을 수 있다. OFF-2에서는 같은 네임스페이스의 두 번째 드라이버 때문에 통신 단절 시험을 진행하지 못했다.

흔한 함정: 연결 확인을 위해 펌웨어·통신 설정을 바꾸거나 자동 reset으로 원인 증거를 지우는 것이다. 현재 규칙은 배선 유지, 펌웨어·Protocol Type·ID·속도 변경 금지이며 실기 지령은 OFF 작업이다. L4 뒤 자동 리셋·원점 복귀도 금지한다([PLAN 5절](../../PLAN.md)).

직접 해 보기:

```bash
cat records/sessions/gripper-takeover-2026-11-07.md
rg -n '장비·안전|펌웨어|배선' AGENTS.md
```

다음 실기는 독립 접촉 보정 검증, 그리퍼 지연·간격·동시 스트림, 실제 파지·투입·복구의 선행 조건을 갖춘 뒤 진행한다. 자료 수집 완료가 이 조건을 대신하지 않는다.
