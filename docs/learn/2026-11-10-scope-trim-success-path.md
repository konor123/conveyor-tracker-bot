# 성공 경로 우선: 진행표에서 범위를 줄이는 방법 (2026-11-10)

## 무엇을 했나

11월 9일 현장 세션에서 사용자가 몇 가지 범위 결정을 내렸다. 실패 판정은 사람이 하고 워크플로우가 성공하는 경로에 집중한다. 카메라 노출·화이트밸런스는 고정하지 않는다. 평면 기준판은 한 위치만 찍는다. 예측 방식은 여기서 마무리하고, 그리퍼가 뚜껑을 가리지 않게 컨베이어를 둔다. 11월 10일에는 이 결정 때문에 필요 없어진 단계를 [Progress](../../Progress.md)에서 지웠다. 바꾼 항목 목록은 [11월 10일 worklog](../../records/worklog/2026-11-10.md)에 있다.

## 어떻게 골랐나

1. 결정의 근거를 기록에서 찾는다. 대화 기억에 기대지 않고 [11월 9일 worklog](../../records/worklog/2026-11-09.md)와 [OFF-1 세션 기록](../../records/sessions/OFF-1-2026-11-09.md)에서 "사용자 지시·결정" 문장을 찾았다(`grep -n 사용자 records/worklog/2026-11-09.md`).
2. 결정 하나마다 그 결정이 없으면 필요했던 항목을 찾는다. 예를 들어 "실패 판정은 사람이 한다"가 정해지면 `verifier.py`로 뚜껑 밖 돌·가림 장면을 자동 판정하는 시험과 자동 판정 대 관찰자 혼동행렬은 필요 없다. "가리지 않는 배치"가 정해지면 가림 시간 측정과 가림을 버티는 벨트 표식 관측도 필요 없다.
3. 결정 범위 밖이거나 안전에 관한 항목은 남긴다. 보호 정지·중단 등급·고장 주입은 실패를 *판정*하는 일이 아니라 로봇을 안전하게 *멈추는* 일이라서 지우지 않았다. 결정문에 직접 나오지 않은 항목(낙하 튕김 시험, 재검출·재파지, MODE_SYNCHRONIZED)은 목록으로 만들어 사용자에게 물었다. 답은 MODE_SYNCHRONIZED는 최종 목표라 유지, 나머지 둘은 제거였다(아래 절).
4. 항목을 지울 때는 그 항목을 가리키는 다른 곳(게이트 표, 현장 세션 시작 조건, 합격 기준)도 함께 고친다. 한 곳만 지우면 지운 항목이 다른 칸의 조건으로 남는다.

## 흔한 함정

- **이미 한 일을 지우기**: 완료된 `[x]` 항목과 수집한 bag은 기록이므로 지우지 않는다. 남은 일만 줄인다.
- **문서 사이 불일치**: Progress만 고치면 `PLAN.md`·`TEST_SPEC.md`에는 지운 요구가 남는다. 남은 불일치는 worklog에 적고 따로 맞춘다.
- **결정을 넓게 해석하기**: "성공 경로에 집중"을 "실패 처리를 모두 뺀다"로 읽으면 안전 기능까지 사라진다. 판정(사람이 대신할 수 있음)과 정지(사람이 대신할 수 없음)를 구분한다.

## 명세·시험까지 맞추기

Progress만 고친 뒤 같은 결정을 `PLAN.md`·`TEST_SPEC.md`·`specs/`에도 반영했다. 순서는 다음과 같다.

1. 지운 항목의 핵심어로 저장소 전체를 찾는다: `grep -rn -E '혼동|화이트밸런스|조명 2|벨트 표식|가림 시간|TC-VIS-009|TC-BEN-010' PLAN.md TEST_SPEC.md specs src tools`.
2. 요구 자체를 바꾼다. 예: 자동 투입 판정은 FAILURE를 내지 않고 SUCCESS/UNKNOWN만 낸다(PLAN 4.5절, SPEC-200 v0.2, TC-VIS-009-01). 가림 시간 측정 TC는 "가림 없는 배치 확인" TC로 바꾼다(TC-BEN-010-01).
3. interface 상수(`CLASS_BELT_MARKER`, `VerifyDrop.FAILURE`)는 남긴다. msg를 바꾸면 SPEC-010 버전·스냅샷·모든 노드 빌드가 따라 바뀌는데, 값을 안 쓰는 것만으로 결정은 충분히 반영된다. 바꾸는 비용이 이득보다 큰 경우다.
4. `python3 tools/spec/trace.py`로 `specs/TRACE.md`를 다시 만든다. 이 파일은 손으로 고치지 않는다. 지운 TC가 행렬에서 빠졌는지, M0 검사(`--gate M0 --check`)가 그대로 0인지 확인한다.

## 문서가 아니라 코드에 있는 기능을 지울 때: L1 재시도

재검출·재파지는 Progress 한 줄이었지만 M0에서 이미 구현되어 있었다. 오케스트레이터의 중단 등급 L1이 그 기능이다. 문서만 지우면 코드는 여전히 재시도하므로 다음 순서로 걷어냈다.

1. **사용처 전부 찾기:** `grep -rn -E 'L1|retry_left|retryable|retries_used|detect_stone_count|pick_stone_count' src tools`. 판단(`abort_policy.decide`), 실행기(`cycle_runner`의 재시도 횟수·검출 나이 재검출), 전이(`state_machine`의 L1·PRECONDITION → DETECT_STONE), 설정(`orchestrator.yaml`의 `retry:`), 노드(`orchestrator_node`)에 흩어져 있었다.
2. **판단 문맥 줄이기:** `AbortCtx`의 재시도 관련 필드(남은 횟수, 재시도 가능 여부, 현재 시각, 예상 소요시간, deadline)는 L1 판정에만 쓰였다. 기능을 지우면 필드도 지운다. 남겨 두면 아무도 읽지 않는 값을 시험마다 채우게 된다.
3. **wire 값은 비워 둔다:** `TaskStatus.abort_level`의 값 1을 다른 뜻으로 다시 쓰거나 2~4를 당기지 않았다. 기록(`records/trials`)과 메시지 소비자가 숫자로 등급을 읽으므로 번호를 바꾸면 과거 기록 해석이 틀어진다. `AbortLevel` enum에서는 L1을 지웠다.
4. **명세 표를 시험과 함께 고치기:** `decide_table.csv`(SPEC-110 기대표)는 재시도 열을 지우면서 행이 288 → 144로 줄었다. 장애 10종 표(`fault_expectations.yaml`)의 `gripper_miss` 기대 등급은 NONE(재시도로 처리) → L2로 바뀌었다. REQ-ORC-006 번호는 유지하고 내용만 "재시도하지 않는다"로 바꿔 M0 추적 행렬(REQ 49·TC 93)이 그대로 맞게 했다.
5. **같은 결과를 다른 경로로 기대하던 시험 찾기:** `test_resume_requires_reason`은 검출 실패 3회(첫 시도 + 재시도 2회) 뒤 재개하는 대본이었다. 재시도가 없어지자 재개 뒤 시도가 대본의 실패 응답을 받아 실패했다. 대본을 실패 1회 + 성공 1회로 고쳤다. 기능을 지울 때 직접 관련 시험만이 아니라 그 기능의 횟수를 전제로 짠 대본도 깨진다.

낙하 튕김 시험(TC-BEN-009-01, `records/templates/drop-prelim.csv`)도 지웠다. 해제 게이트 `e_xy_max`는 실측 허용 오차 대신 치수식 `0.5 × (D_in − d_stone_max) / 2`로 정한다.
