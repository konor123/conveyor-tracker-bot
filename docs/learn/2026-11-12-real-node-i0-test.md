# 손으로 성공시킨 실험을 자동 시험으로 바꾸기

2026-11-12, cy + Claude Code. 관련: [11월 12일 worklog](../../records/worklog/2026-11-12.md), TEST_SPEC TC-INT-009-01.

## 왜 필요한가

11월 11일에 계획 시점(도달 구간 진입 3 s 전부터)과 계획 단계 기준(3.25 mm)을 바꿔서, mock 로봇·카메라 + 실제 tracker·planner로 한 사이클을 4번 성공시켰다. 하지만 그건 손으로 돌린 실험이라, 누가 나중에 tracker 설정이나 오케스트레이터 판정을 바꿔 사이클이 다시 막혀도 아무도 모른다. 자동 시험이 있으면 시험을 돌릴 때마다 바로 드러난다.

## 무엇을 확인하나

| 확인 | 의미 |
|---|---|
| seed 0~3 모두 SUCCESS, 상태 13단계 순서 | 사이클이 끝까지 간다 |
| `drop/intercept_plan` 발행자가 `intercept_planner_node` 하나 | mock의 임시 plan이 아니라 진짜 planner 결과로 성공했다 |
| WAIT_CAP `t_to_window_s` ≤ 3.0 s | 계획을 너무 일찍 요청하지 않았다 |
| PLAN_INTERCEPT `position_std_m` ≤ 3.25 mm | 계획 단계 기준을 지켰다 |

## 시험이 진짜로 잡아내는지 확인(변이 시험)

통과하는 시험이 항상 좋은 시험은 아니다. 고친 부분을 일부러 되돌렸을 때 실패해야 쓸모가 있다. `plan_lead_s`를 3.0에서 100.0으로 바꾸면(= 계획 시점 늦추기를 없앰) 시험이 `CYCLE_TIMEOUT`으로 실패했다. 확인 뒤 값은 되돌렸다.

## 한계

mock 카메라 검출에는 잡음이 없다. 실제 벨트에서는 속도 추정이 덜 정확해서 `position_std_m`이 더 커질 수 있다. 이 시험은 "코드끼리 제대로 이어지는지"를 보는 것이고, 실제 성능(G4)은 현장 측정으로 따로 확인한다.

## 추가: 한 번 받은 예측값을 계속 믿으면 생기는 버그 (REQ-ORC-018)

오케스트레이터는 병뚜껑을 고르는 순간 tracker가 준 "도달 구간 진입 예상 시각"을 한 번 받아 끝까지 썼다. track이 막 생긴 직후에는 속도 추정이 거의 0이라, 진입 시각이 실제보다 수~수십 초 늦게 잡힌다. 그 값을 믿고 "아직 이르다"며 기다리는 동안 뚜껑은 지나가 버린다.

- 잡음 없는 mock은 속도가 몇 프레임 만에 맞아서 이 버그가 안 보였다. 실영상 자료(`caps.csv`)를 재생해야 드러났다.
- 고친 방법: 관측할 때마다 현재 위치·속도로 `(x_reach_start − x) / v`를 다시 계산한다. 실영상에서 계획 시작이 실제 진입 1.3~5.2 s 전으로 맞춰졌다(옛 방식은 진입 뒤까지 밀린 경우가 많았다).
- 대가: 도달 구간 시작 위치를 오케스트레이터 설정에도 적어야 한다. 같은 값이 여러 패키지 설정에 있으면 현장에서 하나만 바꾸는 실수가 생기기 쉽다.
